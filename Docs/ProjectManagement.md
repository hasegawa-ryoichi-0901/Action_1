# プロジェクト管理

## 1. 企画概要

- 仮タイトル: `Temple Guardian`
- 目標: `15〜30分`で遊び切れる短編ダークファンタジーのボスアクションゲームを完成させる
- 成功条件: 広いソウルライクではなく、満足度の高いボス戦を1つ成立させる
- 対応プラットフォーム: `Windows PC`
- 現在のリポジトリ基盤: `Unity 6 URP`

## 2. 固定方針

### 2.1 エンジン前提の統一

元の要件定義書は `Unreal Engine 5.x` 前提だが、このリポジトリはすでに `Unity 6`、`URP`、`Input System`、`UniTask`、独自の `SAM` UI/Context パターンで構成されている。

そのため、この企画は今後以下を正式前提とする。

- エンジン: `Unity 6.0.4f1`
- 描画: `URP`
- 入力: `Unity Input System`
- アーキテクチャ基盤: 既存 `SAM_Template`

これは単なる注記ではない。今後の計画、アセット選定、実装見積もりはすべて Unity 前提で判断する。

### 2.2 スコープ制約

MVP制作中は、以下を固定し拡張しない。

- プレイヤー武器 `1種類`
- メインマップ `1つ`
- ボス `1体`
- 通常敵 `2種類`
- 総プレイ時間 `15〜30分`
- インベントリなし
- クエストシステムなし
- オンライン・協力プレイなし
- マルチエンディングなし
- 大きな物語レイヤーなし

追加したくなった案は、制作範囲に入れず必ず Backlog に送る。

## 3. 現状認識

### 3.1 現在のリポジトリ状態

現在のコードベースはまだテンプレート段階である。

- ゲーム本編のコアループは未実装
- タイトル遷移は未完成
- 本企画用のプレイヤーコントローラは未実装
- 戦闘、敵AI、ボス、セーブ、成長要素は未実装
- この管理対応とは別に未コミット変更が存在する

### 3.2 スケジュール上の注意

元の要件定義書では合計工数は約 `385h` だが、ディレクター方針では実作業可能時間は `250〜300h` 程度を想定している。

管理判断としては以下の通り。

- 元の機能一覧は、実装を意図的に最小化しないと成立しない
- コンテンツ量よりボス品質を優先する
- 見た目の磨き込みは、通しプレイ可能なループ完成後まで後ろ倒しにする

## 4. MVP定義

以下がすべて満たされたときに MVP 完成とみなす。

- タイトル画面からゲーム開始できる
- プレイヤーが移動、攻撃、回避、被弾、回復、死亡できる
- スタミナで攻撃と回避を制限できる
- 小規模な神殿ルートを開始地点からボス部屋まで通せる
- 通常敵2種が一連の流れで機能する
- チェックポイント1つでリトライ導線が成立する
- 読める攻撃 `3種類` を持つボスが倒せる
- クリア後にタイトルへ戻れる
- Windowsビルドでタイトルからクリアまで重大不具合なく通せる

## 6. 制作フェーズ

### Phase 0: 企画の再固定

目的:
- UE前提の企画を Unity 制作計画へ変換し、スコープを固定する

完了条件:
- この管理文書が存在する
- Backlog が分離されている
- 最初の実装順が固定されている

### Phase 1: コアプレイアブル

目的:
- 仮アセットと仮UIでゲーム感触を成立させる

完了条件:
- プレイヤーが移動、攻撃、回避、回復、死亡、再開できる
- 敵1体がプレイヤーにダメージを与え、倒される

### Phase 2: 縦切り完成

目的:
- タイトルからボス挑戦までを1本の流れで通す

完了条件:
- タイトル -> 探索 -> チェックポイント -> ボス -> クリア/ゲームオーバー が成立する

### Phase 3: コンテンツ完成

目的:
- 敵2種目、ボス行動、成長、セーブを揃える

完了条件:
- 見た目が粗くても MVP に必要な全システムが揃っている

### Phase 4: 仕上げと公開準備

目的:
- 安定化、調整、パッケージ化、公開素材準備を行う

完了条件:
- Windowsビルドが安定している
- スクリーンショットと短いPV素材が撮れる

### 8.3 月末レビュー

各月の末日に、以下を確認する。

- 当月成果物が完成しているか

- Backlogに送るべき追加案が混入していないか
- ボス品質を損なわずに削れる要素があるか

### 8.4 遅延時の削減順

進行が遅れた場合は、以下の順で削る。

1. 見た目の磨き込み
2. ボスフェーズ2の複雑さ
3. 敵Bの行動数
4. 成長要素の段階数
5. ロックオンの磨き込み

以下は削らない。

1. プレイヤーの基本操作品質
2. ボス戦の可読性
3. リトライ導線
4. Windowsビルドの安定性

## 11. リスクと対応

| リスク | 影響 | 対応 |
|---|---|---|
| 要件書とリポジトリでエンジン前提が違う | 計画がぶれる | Unity を正式前提として即固定する |
| ボス実装が難航する | 企画の核を失う | 最初は3攻撃だけで成立させ、後から増やす |
| カメラの視認性が悪い | 理不尽な戦闘になる | 狭すぎる地形を避け、グレーボックス段階で検証する |
| スコープ肥大化 | 完成しない | MVP外要素はすべて Backlog に隔離する |
| UI調整に時間を使いすぎる | スケジュール遅延 | 最初は最低限の機能UIで進める |
| アセット統合で詰まる | 導入時間を浪費する | 先に少数の有力アセットだけ検証する |

## 12. システム別完了条件

### プレイヤー

- 移動感が自然である
- 攻撃、回避、回復が入力から発火する
- スタミナ消費で行動制限できる
- 死亡後にチェックポイントへ戻れる

### 敵

- プレイヤーを認識できる
- 攻撃前の予備動作が読める
- 被弾反応とダメージが安定している

### ボス

- 登場演出トリガーが機能する
- ボスHP UIが正しく表示される
- すべての攻撃が視覚的に読める
- 撃破からクリアまでの流れが完了する

1. 見た目の磨き込み
2. ボスフェーズ2の拡張
3. 敵バリエーション
4. 成長要素の深さ

以下は削らない。

1. プレイヤーの分かりやすさ
2. ボスの分かりやすさ
3. リトライ導線
4. ビルド安定性
